# Ночной дневник
Заданный пользователем визуальный мир и структура являются источником решения: специализированный action-first экран, карточка последнего кормления/таймера, сетка 2×2, события, системный таббар. Режим Operate. Цвет усиливает смысл, а подписи и SF Symbols работают без различения цвета. Системный SF, относительные размеры, минимум 44 pt, карточки действий минимум 112 pt. Кремово-жёлтый — кормление, голубой — подгузник, сиреневый — сон. Тёмные варианты сохраняют контраст без ярких светлых заливок ночью. Модальные формы только для подробностей и исправлений; быстрые события сохраняются сразу. Нет обязательной регистрации или настройки сети.


## Дизайн-система приложения

Источник общих значений — `Sources/DesignSystem.swift` (`AppDesign`), компоненты — `Sources/DesignComponents.swift`. Это выделение уже существующего оформления, а не новая визуальная тема. Системные `Form`, `List`, навигация, tab bar, alert и action sheet сохраняют нативное поведение. Не нужно заменять их собственной системой контролов.

### Цвет

| Роль | API | Источник |
| --- | --- | --- |
| Интерактивный акцент | `Palette.accent` | Asset `AccentColor` |
| Текст на заполненной акцентной кнопке | `Palette.onAccent` | Asset `OnAccent`: белый в светлой теме, чёрный в тёмной |
| Кормление грудью и бутылочка | `Palette.feeding` | Asset `Feeding` |
| Подгузник | `Palette.diaper` | Asset `Diaper` |
| Сон | `Palette.sleep` | Asset `Sleep` |
| Фон экрана | `Palette.groupedBackground` | `systemGroupedBackground` |
| Нейтральная карточка | `Palette.cardBackground` | `secondarySystemGroupedBackground` |
| Основной/вторичный текст | `Palette.primaryText` / `secondaryText` | Семантические цвета системы |
| Ошибка / успех | `Palette.error` / `success` | Существующие системные `.red` / `.green` |
| Отметки графика: кормление / подгузник / сон | `Palette.chartFeeding` / `chartDiaper` / `chartSleep` | Существующие системные `.orange` / `.blue` / `.purple` |

Светлые и тёмные варианты определяются существующими assets и системными цветами. Не добавлять отдельные hex-значения на экранах и не угадывать тему по категории продукта: ночью адаптация должна оставаться системной. Тип события всегда обозначается подписью и SF Symbol, а не только цветом. Отметки графика сохраняют более насыщенные системные цвета для различимости небольших marks; их не заменяют пастельными фонами карточек. Для текста заполненных кнопок с `Palette.accent` используйте `Palette.onAccent`: существующий акцент тёмный в светлой теме и светлый в тёмной. Не наследуйте `primaryText` на всём контейнере с такими кнопками. Нативные button style и роли сохраняются; обычные подписи и plain-плитки используют основной цвет отдельно. Ошибка и успех также имеют свои смысловые цвета, а не цвет категории ухода.

### Интервалы, форма и типографика

| Назначение | Значение и API |
| --- | --- |
| Связанные строки | `Spacing.related = 4` |
| Группа деталей | `Spacing.group = 8` |
| Содержимое карточки действия | `Spacing.cardContent = 10` |
| Строки и сетка | `Spacing.row = 12` |
| Внутренний отступ плитки действия | `Spacing.actionInset = 16` |
| Контент экрана и крупной карточки | `Spacing.contentInset = 20` |
| Основные секции | `Spacing.section = 24` |
| Скругление карточки | `Radius.card = 20` |
| Знак бренда и его скругление | `Metrics.brandMarkSize = 48`, `brandMarkCornerRadius = 14` |
| Минимальная цель нажатия | `Metrics.minimumTouch = 44` |
| Минимальная высота содержимого плитки до padding | `Metrics.actionMinimumHeight = 112` |
| Заголовок элемента | `Typography.itemTitle = .headline` |
| Детали | `Typography.detail = .subheadline` |
| Примечание и автор | `Typography.note = .caption` |

Все размеры — pt. Шрифты остаются относительными системными стилями SF, с поддержкой Dynamic Type. Знак бренда закреплён в `Metrics`, чтобы его размер и скругление не расходились. Уникальные размеры графиков и специфические интервалы не превращаются в глобальные токены только потому, что выражены числом. Не нужно заменять каждый `.body`, `.title` или единичный literal псевдоабстракцией.

### Общие компоненты

- `ActionTile(title:subtitle:symbol:color:id:action:)` — четыре быстрых действия на главном экране. Сохраняет `.plain` button style, SF Symbol, текстовую иерархию и accessibility identifier. При accessibility-размере шрифта сетка экрана становится одноколоночной.
- `EventRow(event:authorLabel:action:)` — одна и та же запись в «Сегодня» и истории. При обычном размере — иконка, детали и время; при accessibility-размере — вертикальный блок. `authorLabel` необязателен; при `nil` строка не добавляется и старое отображение сохраняется. Компонент только показывает переданный текст автора, не вычисляет личность и не подставляет текущего родителя для старых записей.
- `.diaryCard(color:inset:)` — существующая поверхность карточки: выравнивание слева на всю ширину, внутренний отступ 20, фон и скругление 20. Модификатор не задаёт цвет текста вложенным контролам. Для плитки действия передаётся отступ 16. Карточка не добавляет тени, собственные анимации или обработчики нажатия.

Для нового сценария сначала использовать эти компоненты. Новый компонент/токен выделять, когда есть минимум три применения с одним назначением; совпадающие цифры у разных элементов сами по себе не причина объединять их. `EventRow` уже был общим компонентом двух экранов и перенесён как есть, без создания дополнительной абстракции.

### Нативные взаимодействия и доступность

Отступы и внешний вид не должны менять место привязки системного окна. `confirmationDialog` остаётся непосредственно на вызывающей кнопке/плитке; модификатор карточки не переносит диалог на общий контейнер. `alert` с явной отменой остаётся там, где нужна постоянно видимая отмена. Существующие роли кнопок, обработчики, accessibility identifiers и адаптация к крупному тексту сохраняются.

`Form`/`List` продолжают использовать системную группировку. Не вводить фиксированную высоту текста, принудительное уменьшение шрифта и обрезку длинных имён или заметок. Полный экран, карточки и строки проверяются в обеих темах; доступность не сводится к визуальным эталонам.

## Детерминированная галерея и визуальные эталоны

`Sources/DesignSystemGallery.swift` компилируется только в DEBUG. `DesignSystemGallery()` использует реальные общие компоненты и статические примеры: четыре действия, карточки кормления/сна, строки событий с автором и без него. Даты, UUID, русский locale и GMT фиксированы; пользовательские данные, AppStore, CloudKit, сетевые вызовы и тикающие таймеры не используются. Ширина, масштаб, тема и Dynamic Type задаются тестовым renderer.

Автоматический контракт — `Tests/DesignSystemSnapshotTests.swift`, тест `DesignSystemSnapshotTests/testGallerySnapshots`. Он рендерит четыре варианта через `ImageRenderer` с масштабом 1: 402×1700 для обычного текста и 402×2800 для крупного. Эталоны лежат в `Tests/DesignBaselines/iOS-<major>/`: `gallery-light-large.png`, `gallery-dark-large.png`, `gallery-light-accessibility3.png`, `gallery-dark-accessibility3.png`. Отсутствующий baseline в обычном прогоне считается ошибкой.

Для записи используется явный режим `RECORD_DESIGN_BASELINES=1`: он прикладывает четыре PNG и manifest, затем помечает тест как пропущенный. Это запись candidates, а не успешное сравнение. Для iOS 26 такой режим запускается вручную через `workflow_dispatch` с `record_baselines=true`; локальные эталоны другой major-версии ОС хранятся отдельно. После просмотра нужно экспортировать и принять PNG в соответствующий каталог и запустить обычное сравнение. Скрипт `Scripts/check-design-system.py` дополнительно проверяет соблюдение правил общих стилей в исходниках; он не заменяет просмотр изображений.

Обязательная матрица — светлая и тёмная тема × обычный `.large` и крупный `.accessibility3` текст. Сравнивать нужно изображения при одинаковых iOS runtime, ширине, масштабе, locale и настройках renderer. Эталоны разных версий iOS не смешиваются: SF Symbols и нативное отображение могут меняться вместе с ОС.

Процедура изменения:

1. Запустить render-тесты против существующих эталонов, сохранив candidate и diff при несовпадении.
2. Разобрать отличия: реальная регрессия, ожидаемая правка оформления или смена платформенного renderer. Не перезаписывать эталон автоматически ради зелёного CI.
3. При намеренном изменении проверить все четыре варианта, отсутствие обрезки и сохранение размеров целей нажатия. Обновить соответствующие эталоны отдельным осмысленным изменением вместе с причиной.
4. Подтвердить автоматическое сравнение после принятия новых эталонов и выполнить затронутые функциональные проверки.

Галерея проверяет воспроизводимость общих стилей и раскладки. Она не доказывает работу системных popup, CloudKit, Live Activities, widget, жестов или VoiceOver; эти сценарии проверяются отдельно. Наличие процедуры и исходника галереи не означает, что конкретный прогон уже прошёл: фактический результат фиксируется в документации проверки.
