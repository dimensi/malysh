# Настройка iCloud и проверка синхронизации

## Подписание и контейнер

Для подписанной сборки и полноценной проверки нужны платная Apple Developer Program, доступ к команде разработчика и два физических iPhone с поддерживаемой версией iOS. Назначьте приложению свою команду и зарегистрируйте заданный Bundle ID `dev.dimensi.malysh` в настройках проекта. Зарегистрируйте контейнер `iCloud.dev.dimensi.malysh`, разрешите его для App ID и включите возможности iCloud / CloudKit и Background Modes / Remote notifications. Обновите provisioning profiles после изменения возможностей.

Проверьте, что подписанная сборка содержит entitlement `com.apple.developer.icloud-container-identifiers` с `iCloud.dev.dimensi.malysh`, сервис `CloudKit` и корректное значение `com.apple.developer.icloud-container-environment`. Сборки разработки должны использовать Development, а распространяемые сборки — Production. В проекте значение задано через `$(CLOUDKIT_ENVIRONMENT)`: Dev и Debug → Development, Release → Production. APNs сохраняет исходную настройку development; при экспорте для распространения Xcode формирует подпись по distribution-профилю. Подписание и provisioning profile должны разрешать выбранную среду. Одного изменения файла недостаточно без настройки Apple Developer.

Контейнер должен принадлежать выбранной команде. Без настроенной команды запуск на симуляторе проверяет только локальное поведение и не доказывает работу CloudKit.

## Схема Development и Production

Для экспорта живых схем, validation и проверки совместимости используйте `bash Scripts/cloudkit-schema.sh`; [инструкция автоматизации](CloudKitSchema.md) описывает авторизацию, diff и проверку после ручного развёртывания в Console.

Первую инициализацию схемы выполняйте вручную только из DEBUG-сборки, подключённой к Development. Дождитесь создания типов записей Core Data / CloudKit, проверьте их в CloudKit Console и разверните схему из Development в Production до тестирования распространяемой сборки. Не вызывайте инициализацию схемы автоматически при обычном запуске и не включайте её в Release.

Development и Production — разные среды. Данные между ними не переносятся при развёртывании схемы. Оба тестовых устройства должны использовать одну среду и одну версию схемы.

## Малыш Dev рядом с обычным приложением

Откройте `Malysh.xcworkspace`, выберите схему **Malysh** и свой iPhone. ⌘R использует конфигурацию `Dev` и устанавливает «Малыш Dev» с бирюзовой иконкой. Тесты схемы используют `Debug`, архив использует `Release`. Для повседневной разработки на телефоне выбирайте именно схему **Malysh**.

При первой настройке в Apple Developer зарегистрируйте два explicit App ID — `dev.dimensi.malysh.dev` и `dev.dimensi.malysh.dev.widgets`. Назначьте обоим App Group `group.dev.dimensi.malysh.dev`. Для App ID приложения включите iCloud / CloudKit и Push Notifications, зарегистрируйте и привяжите только `iCloud.dev.dimensi.malysh.dev`. Xcode создаст development-профили автоматически. У виджета из облачных возможностей есть только App Group.

Проверьте подписи приложения и виджета перед установкой. В обоих должна быть только dev-группа, в приложении дополнительно только dev-контейнер, среда `Development` и development APNs. Один раз запустите с аргументами `--initialize-cloudkit-schema`, `-cloudEnabled` и `YES` и дождитесь `SCHEMA_INITIALIZATION_SUCCEEDED` в консоли. `-cloudEnabled YES` включает iCloud только для этого запуска, в том числе на чистой установке. Затем уберите все три аргумента. Для «Малыш Dev» достаточно схемы Development в его контейнере.

В чистой установке создайте тестовый дневник и при необходимости включите iCloud. Dev использует отдельные локальные данные, облачные записи и ссылки `malysh-dev://`. Для проверки совместной синхронизации оба устройства должны использовать «Малыш Dev» и актуальную схему его контейнера. Проверка Production выполняется на TestFlight.

## Локальное хранение и включение

iCloud по умолчанию выключен. Переключатель переоткрывает те же локальные SQLite-файлы внутри приложения и сохраняет выбранный дневник и активные таймеры. Подключение к iCloud и доставка записей продолжаются после открытия базы.

При первом запуске пустая локальная база открывает онбординг. Дневник создаётся по действию «Создать дневник» и доступен без iCloud. После переустановки действие «Восстановить из iCloud» включает синхронизацию в открытом приложении. Если локальных дневников ещё нет, приложение ждёт импорта private и shared stores. При сбое можно повторить проверку или продолжить локально.

Системное приглашение сохраняется до выбора соответствующего дневника. Если iCloud выключен, приложение включает синхронизацию и продолжает с сохранённым приглашением после готовности iCloud. Успешное принятие запускает ожидание импорта. Приложение проверяет идентификатор share у общего профиля и открывает «Сегодня», когда находит его. На пути подключения личный профиль не создаётся.

Оставшийся от старой версии профиль «Малыш», который система распознала как стартовый, скрывается из основного переключателя при появлении семейного дневника. Для удаления используется кнопка «Удалить лишний Малыш» в разделе «Семья» с явным подтверждением. Профиль «Малыш», явно созданный в онбординге, остаётся в переключателе.

Раздел «Семья» показывает владельца и участников, включая статусы принятого, ожидающего и прекращённого доступа. Владелец включается явно, даже если полученный список участников не содержит отдельной строки владельца. Для каждого родителя можно задать обычное имя и роль «Папа», «Мама» или «Родитель»; текущий пользователь дополнительно отмечается «Это вы». Роль родителя не меняет права CloudKit: управление доступом остаётся в системном экране общего доступа. Пока имя не заполнено, используется доступное имя из CloudKit или «Другой родитель»; адреса почты, телефоны и служебные идентификаторы не выводятся.

Имена и выбранные роли родителей сохраняются в существующем JSON payload профиля ребёнка и передаются вместе с общим дневником. Старые payload без этих полей читаются с пустыми профилями родителей. Новые типы или поля Core Data / CloudKit для этого не добавляются, поэтому отдельное развёртывание схемы не требуется. Локальный долговечный JSON-кэш хранит версии записей родителей: при получении payload изменения объединяются по отдельным родительским профилям и их ревизиям, чтобы восстановить обновления после перезаписи целого payload конкурентной версией. Это отдельное правило для профилей родителей, а не объединение полей событий ухода. Локальные и офлайн unit-тесты проверяют эти преобразования и восстановление кэша, но не доказывают доставку и сходимость между двумя реальными Apple ID.

Синхронизация асинхронная и не мгновенная. Доступность сети, iCloud и фонового выполнения влияет на сроки доставки. Сразу после локального сохранения запись должна быть доступна на этом устройстве даже без сети.

## Проверка двух устройств

Используйте два подписанных физических устройства с разными Apple ID, включённым iCloud и разрешёнными функциями общего доступа. Не публикуйте в отчёте Apple ID, ссылки приглашений или личные записи.

1. Установите сборку одной среды на оба тестовых устройства. На первом устройстве создайте тестовый дневник. Проверьте цикл включения, отключения и повторного включения iCloud без закрытия приложения. Убедитесь, что выбранный дневник, записи и активный таймер сохраняются, а синхронизация возобновляется.
2. На первом устройстве добавьте записи разных типов и создайте приглашение для второго участника. Сверьте фирменную миниатюру в системном окне. Для дневника, которым поделились в прежней версии, снова откройте «Управлять доступом» от имени владельца и проверьте появление миниатюры.
3. На втором устройстве откройте приглашение под другим Apple ID на чистой установке с выключенным iCloud. Дождитесь подключения к iCloud и появления общего дневника и записей без закрытия приложения. Проверьте повторный запуск во время импорта и после него, выбор именно приглашённого дневника и отсутствие личного профиля.
4. Создайте и измените записи по очереди на обоих устройствах. Сверьте время, длительность, объём, типы и заметки после доставки изменений.
5. Отключите сеть на одном устройстве. Создайте и отредактируйте записи локально, перезапустите приложение и убедитесь, что данные сохранены. Подключите сеть и проверьте доставку на второе устройство.
6. Отредактируйте одну запись на обоих устройствах без сети. После подключения проверьте сходимость. Core Data использует `NSMergeByPropertyObjectTrumpMergePolicy` при локальном сохранении, а CloudKit разрешает сетевые конфликты. Payload события — одно атомарное поле: изменения двух родителей не объединяются по отдельным полям. `modifiedAt` сохраняется для учёта, но собственного правила «побеждает максимальное modifiedAt» в MVP нет. Одновременное редактирование одной записи может потерять одну из версий; сходимость нужно проверить на двух устройствах.
7. Удалите запись и проверьте её исчезновение на втором устройстве после синхронизации. Отдельно проверьте удаление без сети и конфликт удаления с редактированием; убедитесь, что устройства сходятся и запись не появляется снова после перезапуска.
8. Проверьте отзыв доступа участника и повторный запуск. Зафиксируйте наблюдаемое поведение и задержки, не предполагая мгновенного обновления.

Если приглашение, конфликт или удаление не проверены, отметьте это явно. Результаты, версии систем, среду контейнера и ограничения записывайте в [Validation.md](Validation.md). На момент подготовки этой инструкции успешная синхронизация двух устройств не заявляется.

## Точные действия для первоначальной схемы

Для подготовки схемы релизного контейнера явно выберите конфигурацию `Debug` для Run и используйте отдельное тестовое устройство без установленного прод-приложения. Убедитесь, что подпись указывает на `iCloud.dev.dimensi.malysh` в среде Development. Для однократной подготовки добавьте в Scheme → Run → Arguments ключ `--initialize-cloudkit-schema`. В этом служебном режиме приложение не открывает пользовательские хранилища дневника: оно вызовет `prepareDevelopmentSchema()`, выведет `SCHEMA_INITIALIZATION_SUCCEEDED` и завершится. Затем уберите аргумент и верните Run в `Dev`. В Release этот код не компилируется.

Инициализатор использует отдельный временный SQLite и только private scope того же контейнера. Пользовательские private/shared-хранилища дневника он не меняет. Нельзя вызывать `initializeCloudKitSchema` непосредственно на рабочем контейнере с shared store. Стандартный API Apple загружает собственные образцовые записи со всеми полями модели и удаляет эти образцы после создания схемы; существующие пользовательские данные не удаляются.

В CloudKit Console → Development → Record Types проверьте три типа `CD_BabyRecord`, `CD_EventRecord` и `CD_MeasurementRecord` вместе с полями/индексами. Одного профиля ребёнка недостаточно: он не создаёт тип событий. Выберите Deploy Schema Changes и просмотрите изменения для Production. После развёртывания убедитесь, что все три типа появились в Production. Перезапустите TestFlight-сборки на обоих телефонах и повторите приглашение. Подготовка и перенос схемы выполняются явно; штатный запуск и CI не делают этого автоматически.

## Одновременные таймеры и отзыв доступа

Независимо запущенные офлайн таймеры имеют разные UUID и после доставки видны отдельными карточками. Приложение не удаляет и не объединяет их автоматически: завершите и при необходимости исправьте дубли вручную.

На iOS 17 системные изменения Sharing обрабатываются Core Data автоматически. После отзыва доступа участника ожидается импорт удаления из shared store. Отключение iCloud сохраняет уже загруженные локальные данные.

В разделе «Управление дневниками» удаление дневника владельцем удаляет его содержимое и завершает общий доступ. Выход участника удаляет зону из его shared database и сохраняет дневник у владельца. «Начать заново» обрабатывает зоны текущего аккаунта в среде установленной сборки, включая ещё не загруженные в приложение, затем открывает первый экран настройки. Для облачного сброса нужно включить синхронизацию и дождаться её готовности.

На двух тестовых Apple ID проверьте отдельно выход участника, удаление владельцем и полный сброс. После перезапуска и синхронизации у вышедшего участника должен исчезнуть чужой дневник, а у владельца должны остаться его записи. После удаления владельцем дневник должен исчезнуть у обоих. После полного сброса у инициатора должен появиться первый экран настройки при пустом хранилище. При обрыве сети проверьте сообщение об ошибке и повторите сброс после восстановления связи.

`cloudSharingControllerDidSaveShare` только уведомляет интерфейс. Он не вызывает `persistUpdatedShare`: начиная с iOS 16.4 Core Data самостоятельно наблюдает сохранения системного экрана. `persistUpdatedShare` остаётся только для собственных изменений приложения перед открытием системного экрана (заголовок и права). После принятия приглашения приложение ждёт импорта и выбирает профиль по ID принятого share, а не первый доступный общий профиль.

API сверены с [документацией Apple по общему доступу Core Data](https://developer.apple.com/documentation/coredata/sharing-core-data-objects-between-icloud-users) и [приёму приглашений в SwiftUI](https://developer.apple.com/documentation/coredata/accepting-share-invitations-in-a-swiftui-app).

## Если приглашение возвращает Bad Container

Это означает неизвестный или недоступный приложению контейнер, а не ошибку локального дневника. Сверьте точное имя контейнера в `Info.plist`, подписи готовой `.app`, provisioning profile и CloudKit Console выбранной Team. Для запуска из Xcode в Dev или Debug итоговая подпись должна содержать `com.apple.developer.icloud-container-environment = Development`. Файл исходных entitlements сам по себе не доказывает, что значение попало в подпись.

После правки требуется пересборка и повторный запуск. Удалять приложение или локальную базу не нужно. Откройте CloudKit Console из Xcode и убедитесь, что контейнер доступен выбранной команде и открывается его Development-среда. После изменения серверной конфигурации нажмите «Попробовать снова» в настройках iCloud, чтобы переоткрыть хранилище при ошибке первоначальной инициализации.

Кнопка приглашения теперь доступна только после успешного setup обоих хранилищ и проверки учётной записи, а не сразу после включения переключателя. Ошибка подключения показывается коротким текстом в настройках.

Через CloudKit Console подтверждено: в Production контейнера был только системный тип Users; Development содержал CD_BabyRecord и cloudkit.share, но не CD_EventRecord. Полная схема затем успешно подготовлена на физическом iPhone отдельным DEBUG-запуском и развёрнута в Production. Проверены CD_BabyRecord (15 полей), CD_EventRecord (17 полей), cloudkit.share (9 полей) и соответствующие индексы. После такого изменения нужно перезапустить приложения, у которых mirroring delegate уже завершился с ошибкой. Проверка обмена между двумя Apple ID выполняется отдельно.

## Схема V3: профиль и измерения

Перед распространением V3 явно повторите DEBUG-подготовку Development по инструкции выше, проверьте новый `CD_MeasurementRecord` и отношения с ребёнком, затем отдельно разверните изменения схемы в Production. PR1 не выполняет инициализацию или deploy схемы. Старые типы и поля не удалять.

На двух Apple ID дополнительно проверить изменение имени/подтверждённой даты, создание всех типов измерений с обеих сторон, редактирование/удаление и перезапуск, офлайн-конфликты одной записи и удаления/редактирования. Локальный тест shared-store доказывает структуру графа, а не доставку CloudKit. Обмен измерениями и сходимость двух реальных Apple ID в PR1 не заявляются проверенными.

## Схема V4: семейные фотографии

V4 сохраняет старые модели и добавляет `PhotoRecord` с обратным отношением `BabyRecord.photos`. Изображение и превью — отдельные Binary Data поля с внешним хранением; JSON содержит только метаданные. Запись относится к тому же store и общему графу ребёнка. Схема требует `CD_PhotoRecord`, `imageData`, `thumbnailData` и отношения `photos`; существующие типы, поля и CKShare не удаляются. 5 ноября 2026 V4 успешно инициализирована на подписанной DEBUG-сборке iPhone; [workflow prepare 42087780812](https://github.com/dimensi/malysh/actions/runs/42087780812) подтвердил совместимость. Его настоящий artifact `snapshot/development.ckdb` сохранён в `CloudKit/development.ckdb`. Production остаётся отдельным ручным этапом перед распространением. Подробности и аппаратная приёмка — [Photos.md](Photos.md).

## Схема V5: первоначальные измерения

V5 добавляет необязательное поле `BabyRecord.birthMeasurementsCompleted`. Core Data автоматически переносит private и shared SQLite, сохраняя версии моделей V2–V4. У существующих профилей поле пустое. При первом сохранении измерений или явном пропуске приложение записывает `true` в том же хранилище. Имя, дата, записи измерений и признак завершения сохраняются одной локальной транзакцией. Измерения связаны с ребёнком как обычные `MeasurementRecord`, поэтому их можно изменить или удалить в истории.

Признак передаётся вместе с общей записью ребёнка отдельным полем CloudKit. Формат JSON профиля остался прежним. Перезапись JSON старой версией приложения и удаление измерений не сбрасывают признак. После получения признака устройство отклоняет повторную отправку из открытой ранее формы. Если два родителя заполнят форму без связи и до получения изменений друг друга, обе записи могут попасть в историю. Такой дубль можно удалить там же.
