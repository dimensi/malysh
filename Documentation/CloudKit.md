# Настройка iCloud и проверка синхронизации

## Подписание и контейнер

Для подписанной сборки и полноценной проверки нужны платная Apple Developer Program, доступ к команде разработчика и два физических iPhone с iOS 26 или новее. Назначьте приложению свою команду и зарегистрируйте заданный Bundle ID `dev.dimensi.malysh` в настройках проекта. Зарегистрируйте контейнер `iCloud.dev.dimensi.malysh`, разрешите его для App ID и включите возможности iCloud / CloudKit и Background Modes / Remote notifications. Обновите provisioning profiles после изменения возможностей.

Проверьте, что подписанная сборка содержит entitlement `com.apple.developer.icloud-container-identifiers` с `iCloud.dev.dimensi.malysh`, сервис `CloudKit` и корректное значение `com.apple.developer.icloud-container-environment`. Сборки разработки должны использовать Development, а распространяемые сборки — Production. В проекте значение задано через `$(CLOUDKIT_ENVIRONMENT)`: Debug → Development, Release → Production. APNs сохраняет исходную настройку development; при экспорте для распространения Xcode формирует подпись по distribution-профилю. Подписание и provisioning profile должны разрешать выбранную среду. Одного изменения файла недостаточно без настройки Apple Developer.

Контейнер должен принадлежать выбранной команде. Без настроенной команды запуск на симуляторе проверяет только локальное поведение и не доказывает работу CloudKit.

## Схема Development и Production

Первую инициализацию схемы выполняйте вручную только из DEBUG-сборки, подключённой к Development. Дождитесь создания типов записей Core Data / CloudKit, проверьте их в CloudKit Console и разверните схему из Development в Production до тестирования распространяемой сборки. Не вызывайте инициализацию схемы автоматически при обычном запуске и не включайте её в Release.

Development и Production — разные среды. Данные между ними не переносятся при развёртывании схемы. Оба тестовых устройства должны использовать одну среду и одну версию схемы.

Обычная команда Run схемы Malysh в Xcode использует Debug/Development. Для сравнения с TestFlight выберите Edit Scheme → Run → Build Configuration → Release: у такой сборки CloudKit Production. Ссылка из Development не является проверкой приглашения в TestFlight Production. Не чередуйте среды на одном рабочем дневнике: локальные SQLite используются те же, а Core Data вынужден обновлять метаданные синхронизации при смене среды.

## Локальное хранение и включение

iCloud по умолчанию выключен. Изменение переключателя применяется после перезапуска приложения. Используется тот же локальный SQLite-файл: режим iCloud не является отдельным профилем данных.

После импорта семейного дневника пустой автоматически созданный профиль «Малыш» скрывается из выбора; основным становится общий профиль. Это не удаление: исходная запись остаётся в базе. Профили с событиями, заданным именем или собственным share сохраняются видимыми; автоматического объединения или переноса записей между private/shared-хранилищами нет. Выбранный семейный профиль сохраняется после повторного запуска.

Раздел «Семья» показывает общий статус, владельца и участников. Владелец включается явно, даже если список участников не содержит отдельной строки владельца. Имена берутся только из доступного локального CloudKit-снимка; если система не отдаёт имя, используется «Другой родитель», а текущий пользователь обозначен «Вы». Эти сведения используются в памяти для отображения и не сохраняются отдельно. Статусы принятого, ожидающего и прекращённого доступа различаются. Приложение не запрашивает дополнительные entitlement для доступа к личности владельца или one-time-link API.

Синхронизация асинхронная и не мгновенная. Доступность сети, iCloud и фонового выполнения влияет на сроки доставки. Сразу после локального сохранения запись должна быть доступна на этом устройстве даже без сети.

## Проверка двух устройств

Используйте два подписанных физических устройства с разными Apple ID, включённым iCloud и разрешёнными функциями общего доступа. Не публикуйте в отчёте Apple ID, ссылки приглашений или личные записи.

1. Установите сборку одной среды на оба устройства. Включите iCloud и перезапустите приложение на каждом.
2. На первом устройстве переименуйте автоматически созданный профиль и добавьте несколько записей разных типов. Создайте приглашение для второго участника.
3. На втором устройстве примите приглашение под другим Apple ID. Дождитесь появления общего ребёнка и записей. Проверьте, что доступ сохраняется после перезапуска.
4. Создайте и измените записи по очереди на обоих устройствах. Сверьте время, длительность, объём, типы и заметки после доставки изменений.
5. Отключите сеть на одном устройстве. Создайте и отредактируйте записи локально, перезапустите приложение и убедитесь, что данные сохранены. Подключите сеть и проверьте доставку на второе устройство.
6. Отредактируйте одну запись на обоих устройствах без сети. После подключения проверьте сходимость. Core Data использует `NSMergeByPropertyObjectTrumpMergePolicy` при локальном сохранении, а CloudKit разрешает сетевые конфликты. Payload события — одно атомарное поле: изменения двух родителей не объединяются по отдельным полям. `modifiedAt` сохраняется для учёта, но собственного правила «побеждает максимальное modifiedAt» в MVP нет. Одновременное редактирование одной записи может потерять одну из версий; сходимость нужно проверить на двух устройствах.
7. Удалите запись и проверьте её исчезновение на втором устройстве после синхронизации. Отдельно проверьте удаление без сети и конфликт удаления с редактированием; убедитесь, что устройства сходятся и запись не появляется снова после перезапуска.
8. Проверьте отзыв доступа участника и повторный запуск. Зафиксируйте наблюдаемое поведение и задержки, не предполагая мгновенного обновления.

Если приглашение, конфликт или удаление не проверены, отметьте это явно. Результаты, версии систем, среду контейнера и ограничения записывайте в [Validation.md](Validation.md). На момент подготовки этой инструкции успешная синхронизация двух устройств не заявляется.

## Точные действия для первоначальной схемы

В Xcode запустите подписанную DEBUG-сборку на iPhone с включённым iCloud. Для однократной подготовки добавьте в Scheme → Run → Arguments ключ `--initialize-cloudkit-schema`. В этом служебном режиме приложение не открывает пользовательские хранилища дневника: оно вызовет `prepareDevelopmentSchema()`, выведет `SCHEMA_INITIALIZATION_SUCCEEDED` и завершится. Затем уберите аргумент. В Release этот код не компилируется.

Инициализатор использует отдельный временный SQLite и только private scope того же контейнера. Пользовательские private/shared-хранилища дневника он не меняет. Нельзя вызывать `initializeCloudKitSchema` непосредственно на рабочем контейнере с shared store. Стандартный API Apple загружает собственные образцовые записи со всеми полями модели и удаляет эти образцы после создания схемы; существующие пользовательские данные не удаляются.

В CloudKit Console → Development → Record Types проверьте **оба** типа `CD_BabyRecord` и `CD_EventRecord` вместе с полями/индексами. Одного профиля ребёнка недостаточно: он не создаёт тип событий. Выберите Deploy Schema Changes и просмотрите изменения для Production. После развёртывания убедитесь, что оба типа появились в Production. Перезапустите TestFlight-сборки на обоих телефонах и повторите приглашение. Подготовка и перенос схемы выполняются явно; штатный запуск и CI не делают этого автоматически.

## Одновременные таймеры и отзыв доступа

Независимо запущенные офлайн таймеры имеют разные UUID и после доставки видны отдельными карточками. Приложение не удаляет и не объединяет их автоматически: завершите и при необходимости исправьте дубли вручную.

На iOS 17 системные изменения Sharing обрабатываются Core Data автоматически. Вызов purge для зоны намеренно отсутствует: он может удалить исходный граф владельца. После отзыва доступа участника ожидается импорт удаления из shared store; сценарий не подтверждён на реальных устройствах. Отключение iCloud сохраняет уже загруженные локальные данные, поэтому это не механизм безопасного отзыва доступа.

`cloudSharingControllerDidSaveShare` только уведомляет интерфейс. Он не вызывает `persistUpdatedShare`: начиная с iOS 16.4 Core Data самостоятельно наблюдает сохранения системного экрана. `persistUpdatedShare` остаётся только для собственных изменений приложения перед открытием системного экрана (заголовок и права). После принятия приглашения приложение ждёт импорта и выбирает профиль по ID принятого share, а не первый доступный общий профиль.

API сверены с [документацией Apple по общему доступу Core Data](https://developer.apple.com/documentation/coredata/sharing-core-data-objects-between-icloud-users) и [приёму приглашений в SwiftUI](https://developer.apple.com/documentation/coredata/accepting-share-invitations-in-a-swiftui-app).

## Если приглашение возвращает Bad Container

Это означает неизвестный или недоступный приложению контейнер, а не ошибку локального дневника. Сверьте точное имя `iCloud.dev.dimensi.malysh` в коде, подписи готовой `.app`, provisioning profile и CloudKit Console выбранной Team. Для запуска из Xcode Debug итоговая подпись должна содержать `com.apple.developer.icloud-container-environment = Development`. Файл исходных entitlements сам по себе не доказывает, что значение попало в подпись.

После правки требуется пересборка и повторный запуск. Удалять приложение или локальную базу не нужно. Откройте CloudKit Console из Xcode и убедитесь, что контейнер доступен выбранной команде и открывается его Development-среда. После изменения серверной конфигурации полностью перезапустите приложение: mirroring delegate мог остаться в состоянии ошибки первоначальной инициализации.

Кнопка приглашения теперь доступна только после успешного setup обоих хранилищ и проверки учётной записи, а не сразу после включения переключателя. Ошибка подключения показывается коротким текстом в настройках.

## Наблюдение 4 ноября 2026: незавершённая схема

Через CloudKit Console подтверждено: в Production контейнера был только системный тип Users; Development содержал CD_BabyRecord и cloudkit.share, но не CD_EventRecord. Полная схема затем успешно подготовлена на физическом iPhone отдельным DEBUG-запуском и развёрнута в Production. Проверены CD_BabyRecord (15 полей), CD_EventRecord (17 полей), cloudkit.share (9 полей) и соответствующие индексы. После такого изменения нужно перезапустить приложения, у которых mirroring delegate уже завершился с ошибкой. Проверка обмена между двумя Apple ID выполняется отдельно.
