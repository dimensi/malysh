# Инструкции для агентов

Если доступен локальный `~/.codex/RTK.md`, прочитайте его и соблюдайте его правила.

## Матрица тестов

- Перед добавлением или изменением тестов прочитайте [Documentation/TestMatrix.md](Documentation/TestMatrix.md). Это действующий перечень рисков, уровней проверки и условий запуска; старые отчёты Validation описывают прошлые прогоны, а не обязательный состав набора.
- По умолчанию расширяйте существующий сценарий. Новый тест допустим для нового пользовательского поведения, отдельной границы хранения/системы или воспроизводимой регрессии, которую текущие проверки не ловят. В изменении укажите строку матрицы и конкретный сбой, который обнаруживает тест; при новом риске сначала дополните матрицу.
- Не добавляйте тест на каждую функцию, ветку реализации, константу, текст подписи или косметическую правку. Одинаковые входные варианты проверяйте таблицей в существующем тесте, если они относятся к одному контракту. Не объединяйте независимые сценарии и не переносите удалённые проверки в мегатесты только ради уменьшения счётчика. Текущий компактный набор — исходный предел: сначала рассмотрите замену существующего теста, рост обоснуйте новым существенным риском.
- Одно правило проверяется на самом дешёвом достаточном уровне. UI-тест нужен для поведения интерфейса или интеграции с iOS; не повторяйте в нём всю матрицу доменных значений, тем и размеров. Миграция, откат, потеря доступа, конфликт и холодный запуск — разные риски, их нельзя удалять как «ещё один happy path».
- Не создавайте новые test targets, фреймворки, галереи PNG, эталонные изображения, сравнение пикселей и отдельные визуальные CI без прямого запроса пользователя. Визуальные состояния проверяйте по ручной части матрицы; скриншот ошибки в обычном UI-тесте допустим.
- После изменения запускайте затронутые строки матрицы. Для релиза полный набор выполняется только в релизном CI до подписи и загрузки; после общей перестройки тестов полный набор также нужен в CI. Не повторяйте успешный прогон без новых изменений или конкретной причины. Для сбоя сначала повторяйте только упавший сценарий. Пропуск или непроверенный ручной сценарий не записывайте как успех.

## Сборки Xcode и Apple Account

- Для фоновых проверок используйте симулятор с локальной ad hoc подписью (`CODE_SIGNING_ALLOWED=YES CODE_SIGN_IDENTITY=-`), как в `Scripts/check.sh`. Не передавайте `-allowProvisioningUpdates` для симулятора.
- Запускайте сборку для физического iPhone или Apple Watch с `-allowProvisioningUpdates`, использующую личный Apple Account из Xcode, только при разблокированном Mac. Если состояние Mac неизвестно или связка ключей заблокирована, отложите этот запуск. При `No Accounts`, `Invalid credentials in keychain` или `-25308` остановите сборку и сообщите о сбое авторизации. Не повторяйте запуск в фоне и не меняйте настройки аккаунта или связки ключей.
- Для подписи и загрузки в TestFlight используйте штатный CI из раздела «Выпуск». CI использует отдельную связку ключей и ключ App Store Connect. При сбое CI диагностируйте упавший этап и не переключайтесь автоматически на локальный выпуск с личным Apple Account.

## Локальные worktree

- Для новых worktree этого репозитория используйте `.worktrees/<имя>` внутри основной рабочей копии. Для этого пути используйте корень основного checkout, даже если команда запускается из другого worktree. Каталог `.worktrees/` игнорируется Git.

## Локальные симуляторы

- У каждого worktree может быть не больше одного выделенного симулятора одновременно. Разные worktree запускают свои симуляторы параллельно, даже если выбрали одну модель. Создавайте экземпляр только при необходимости, с уникальной меткой worktree в имени. Перед созданием проверьте, есть ли уже экземпляр этого worktree, и переиспользуйте его. Для смены модели или версии ОС сначала удалите прежний временный экземпляр своего worktree.
- В каждом локальном прогоне явно указывайте UDID своего симулятора. Для iOS в `Scripts/check.sh` задайте `DESTINATION='platform=iOS Simulator,id=<UDID>'`. Сохраняйте `-parallel-testing-enabled NO`, чтобы Xcode не создавал клоны для тестов.
- После прогона выключите свой симулятор и сохраните его для следующих проверок в том же worktree. После релиза или перед удалением worktree удалите по UDID выделенный ему временный симулятор и очистите временные файлы сборки этой задачи. Сохраняйте результаты, нужные для разбора сбоев и подтверждения релиза. Устройства пользователя и других worktree оставляйте в их распоряжении.

## Выпуск

- По просьбе выпустить готовую ветку используйте `bash Scripts/release.sh vX.Y.Z` из чистого worktree с готовым коммитом; точные параметры и восстановление описаны в [TestFlight.md](Documentation/TestFlight.md). Скрипт выполняет push, PR, слияние, тег, GitHub Release и удаление своей удалённой ветки.
- Не запускайте полный локальный набор повторно перед выпуском: полный набор уже обязателен в релизном CI перед подписью и загрузкой. Не отслеживайте сборку, если пользователь об этом не просил. Сообщайте запуск отдельно от подтверждённой доступности в TestFlight.
- Скрипт не обходит ограничения доступа или требуемые подтверждения; ошибки и частично завершённый выпуск не маскируйте повторной публикацией.

## Схема CloudKit

- Готовый workflow — `.github/workflows/cloudkit-schema.yml`; используйте его, не исследуйте и не создавайте автоматизацию заново. В GitHub Actions → CloudKit schema tooling → Run workflow выберите нужный ref и `prepare` (по умолчанию), `check` или `verify-production`. Зарегистрированный workflow запускается через `gh workflow run cloudkit-schema.yml --ref <ветка-со-схемой> -f operation=prepare`; после merge используйте `--ref main`.
- Контейнер `iCloud.dev.dimensi.malysh`, Team `YBBAN7R28K`; приложение использует Core Data / `NSPersistentCloudKitContainer`, не SwiftData. Для новых полей модели сначала выполните существующую DEBUG-инициализацию Development по [CloudKit.md](Documentation/CloudKit.md).
- `prepare` экспортирует обе среды и проверяет совместимость. Только успешный `prepare` добавляет в CI artifact `snapshot/development.ckdb` рядом с `report.json`: проверьте результат, статус и diff, затем скопируйте снимок в `CloudKit/development.ckdb` и сохраните в Git. Остальные операции публикуют только отчёт. Локальный эквивалент: `bash Scripts/cloudkit-schema.sh`; безопасная проверка: `bash Scripts/cloudkit-schema.sh check`.
- Production переносится вручную через CloudKit Console → Development → Deploy Schema Changes. После этого запустите `verify-production`. Workflow не выполняет production-import, reset, изменение записей или автоматический commit.
- `import-development` предназначен только для явного применения версионируемого файла в Development: отдельное подтверждение `confirm_development_import=true` в CI или `--confirm-import-development` локально. Токен хранится в GitHub secret `CLOUDKIT_MANAGEMENT_TOKEN` либо локально в штатной авторизации cktool; не печатайте его. Полная инструкция: [CloudKitSchema.md](Documentation/CloudKitSchema.md).

## Нативные диалоги SwiftUI

- Для уточняющего выбора после действия используйте системный `confirmationDialog`; для ошибок и важных уведомлений — `alert`. Отдельный `alert` допустим для подтверждения, которому нужна постоянно видимая кнопка отмены.
- Удаление одной записи выполняется сразу, без подтверждения: одинаково по свайпу в истории и кнопкой «Удалить запись» в редакторе. Подтверждение очистки целого дневника — отдельный сценарий; сохраняйте его.
- Прикрепляйте `.confirmationDialog` непосредственно к вызвавшей его кнопке или карточке действия. Не размещайте его на общем `ScrollView`, `Form`, `NavigationStack` или другом контейнере всего экрана.
- Начиная с iOS 26, action sheets на iPhone, как и на iPad, показываются возле элемента-источника. Корректная привязка нужна для положения окна, стрелки и системной анимации. Положение выбирает система: не задавайте координаты и не имитируйте старую нижнюю шторку кастомным popover.
- Для нескольких независимых действий задавайте отдельный диалог на каждом элементе-источнике. Сохраняйте `role: .destructive` для удаления и `role: .cancel` для отмены; в привязанном action sheet система может скрывать кнопку отмены в пользу нажатия снаружи.
- При проверке UI смотрите, что окно появляется возле вызвавшего элемента, в том числе после прокрутки и с крупным Dynamic Type.
- Перед изменением API или поведения сверяйтесь с актуальной документацией через Context7 CLI: сначала `npx ctx7@latest library SwiftUI "<конкретный вопрос>"`, затем `npx ctx7@latest docs <полученный ID> "<конкретный вопрос>"`. Не более трёх запросов на вопрос; не передавайте секреты.

Источники Apple:

- [Human Interface Guidelines: Action sheets](https://developer.apple.com/design/human-interface-guidelines/action-sheets)
- [WWDC25: Build a UIKit app with the new design — Presentations](https://developer.apple.com/videos/play/wwdc2025/284/?time=811)
- [SwiftUI: confirmationDialog](https://developer.apple.com/documentation/swiftui/view/confirmationdialog(_:ispresented:titlevisibility:actions:))


## Общие стили

- Для общих цветов, интервалов, скругления карточек, размеров целей нажатия и повторяющихся текстовых ролей используйте `AppDesign` в `Sources/DesignSystem.swift`. Семантические assets и системные цвета сохраняют светлую/тёмную тему; не дублируйте их локальными hex-значениями.
- Перед созданием собственного аналога проверьте `Sources/DesignComponents.swift`: `ActionTile`, `EventRow` и `.diaryCard(color:inset:)`. Новую абстракцию выделяйте после трёх применений с одним назначением, не токенизируйте каждый literal. Одиночные размеры остаются рядом с соответствующим элементом.
- Сохраняйте относительные SF-шрифты, Dynamic Type, одноколоночную сетку и вертикальные строки при accessibility-размерах. Не маскируйте переполнение уменьшением шрифта или фиксированной высотой текста.
- Извлечение общих стилей не разрешает менять обработчики, роли кнопок, accessibility identifiers или привязку нативных popup. Правила раздела «Нативные диалоги SwiftUI» выше остаются обязательными.
- `EventRow.authorLabel` только отображает уже разрешённую моделью подпись. Не восстанавливайте автора старого события из текущего аккаунта/выбранного родителя и не добавляйте фиктивную подпись, когда автор неизвестен.
- Правила оформления описаны в `DESIGN.md`. При изменении интерфейса проверяйте светлую/тёмную тему и крупный Dynamic Type, запускайте затронутые функциональные UI-тесты. Не добавляйте отдельную инфраструктуру визуальных эталонов без явного запроса.
